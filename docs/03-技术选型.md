## 2. 运行时与语言

### ADR-001：使用 Node.js 便携版而非 Bun 单文件

**背景**：需要在无 Node 的 Windows 机器上零安装运行，同时要求生态成熟、TUI 可用、调试方便。

**候选**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Node 24 便携 zip | 官方签名、生态最全、Ink/MCP SDK 一等支持、调试成熟 | 体积约 80~110MB；启动约 100~300ms |
| Bun `--compile` 单 exe | 单文件、启动快、体积小 | 跨平台交叉编译需验证；部分 Node 原生模块不兼容；调试与生态风险 |
| Deno compile | 单文件、权限模型好 | Node 生态兼容性一般；Ink 运行需额外适配 |
| 依赖系统 Node | 体积最小 | 违背"零安装"核心需求 |

**决策**：Node.js 24 LTS 便携版，放在 `runtime\node-v24.x-win-x64\`。

**理由**：

1. 核心需求是"插上即用"，Node 便携 zip 解压即用，且由官方签名，降低杀软误报；
2. Ink、MCP SDK、各类解析库都对 Node 一等支持，踩坑最少；
3. 调试与性能分析工具链成熟，后期维护成本低；
4. U 盘容量不是瓶颈，100MB 运行时可以接受。

**后果**：

- U 盘写入一次运行时，之后只读使用；升级 Node 时整体替换目录；
- 需要在构建脚本中固定 Node 版本并校验 SHA256；
- 启动器必须使用绝对路径调用 `node.exe`，不能依赖 PATH；
- 运行时目录按平台分：`runtime\win-x64\`、`runtime\linux-x64\`、`runtime\darwin-arm64\`……v1 只装配 `win-x64`，其余留空，保证未来 Linux/macOS 扩展时无需改目录结构。

---

### ADR-002：TypeScript strict + ESM

**决策**：TypeScript 5.x，`strict: true`，`module: NodeNext`，输出 ESM。

**理由**：Agent 核心是异步流与大量接口定义，类型系统显著降低适配层出错率；ESM 与 Ink 6、MCP SDK 对齐。

**约束**：

- 禁止 `any` 逃逸（必要时用 `unknown` + 收窄）；
- 公共接口必须有显式返回类型；
- 单文件 ≤ 800 行，单函数 ≤ 50 行（与项目通用规范一致）。

## 3. 交互层

### ADR-003：Ink 6 + React 作为 TUI

**候选对比**：

| 方案 | 交互能力 | 开发效率 | 体积 | 风险 |
|---|---|---|---|---|
| Ink + React | 高（组件化、焦点管理、流式重绘） | 高 | 中 | React 版本兼容 |
| blessed | 中（传统 widget） | 中 | 中 | 维护活跃度低、Windows 兼容问题 |
| 手写 ANSI | 完全可控 | 低（大量边界） | 最小 | 开发周期长、易出终端兼容 bug |
| Textual (Python) | 高 | 高 | 大 | 需 Python 运行时，与 Node 栈冲突 |

**决策**：Ink 6 + React 19。

**理由**：Claude Code 的交互基线（流式消息、审批弹窗、状态栏）用 Ink 实现最直接；组件模型便于后续扩展。

**降级策略**：

- 检测到不支持 raw mode 的终端（或 `--plain`）→ 使用纯文本逐行输出；
- 所有 UI 组件不参与业务逻辑，保证 headless 完全可用。

### ADR-004：Markdown 渲染

**决策**：`marked` 解析 + 自研 ANSI 渲染器 + `cli-highlight` 做代码高亮。

**理由**：`marked` 轻、稳定；自研 ANSI 渲染可控制宽度、缩进与截断；`cli-highlight` 基于 highlight.js，体积可接受。不选 shiki（体积与启动成本高）。

## 4. 模型接入

### ADR-005：适配器模式 + 原生 fetch

**决策**：不依赖各家 SDK，使用 Node 原生 `fetch` + 自研 SSE 解析，实现 `Provider` 接口。

**理由**：

- 官方 SDK 体积大、版本耦合强，且 Anthropic/OpenAI 两家 SDK 同时引入会显著增加 bundle；
- 两家协议都基于 HTTP + SSE，自研解析可控（超时、重试、代理、自定义 header）；
- 便于支持企业网关与本地 Ollama 等"非标准"端点。

**协议覆盖**：

| Provider | 端点 | 工具调用 |
|---|---|---|
| Anthropic | `POST /v1/messages` | `tools` + `tool_use/tool_result` content block |
| OpenAI 兼容 | `POST /v1/chat/completions` | `tools` + `tool_calls` + `role=tool` |

**差异处理**：

- 并行工具调用：OpenAI 一次性返回多个 `tool_calls`；统一转成多个 `tool_use`；
- 流式工具参数：Anthropic 为 `input_json_delta`，OpenAI 为 `arguments` 分片；统一拼接后 JSON 解析；
- 用量字段：统一映射到 `Usage`，缺失字段置 0 并标记"估算"。
- 能力声明：配置中可关闭 `parallelToolCalls`，不支持时改为串行提示。

**后果**：需要为每家写集成测试（真实 API 冒烟 + 录制回放），这是 v1 的主要测试成本之一。

## 5. 工具与搜索

### ADR-006：内置 ripgrep.exe

**决策**：随盘携带官方 `rg.exe`（x86_64-pc-windows-msvc），放在 `tools\ripgrep\`。

**理由**：

- JS 实现的搜索在大型仓库上明显慢，且要自己处理 ignore 规则；
- ripgrep 原生支持 `.gitignore`、二进制跳过、JSON 输出（`--json`），解析稳定；
- 单个 exe 约 2~3MB，无依赖。

**降级**：`rg.exe` 缺失或执行失败时，回退到 Node 实现的简化搜索（仅文本文件，忽略 `node_modules/.git`），并在结果中标注。

**备选否决**：`git grep` 依赖目标机安装 Git（不保证）；第三方 npm 包（如 `ripgrep-js`）仍需下载二进制。

### ADR-007：工具结果截断与全文落盘

**决策**：上下文内限制 30KB / 2000 行；全文写入 `data\tool-outputs\`。

**理由**：避免单次工具输出撑爆上下文；同时保留可追溯性（模型可按需 Read 全文）。

## 6. 配置与存储

### ADR-008：JSONC 配置

**决策**：`settings.json` / `permissions.json` / `mcp.json` 使用 JSONC（允许注释与尾逗号），用 `jsonc-parser` 解析；`secrets.json` 使用严格 JSON。

**理由**：用户会手工编辑配置，注释能显著降低维护成本；`jsonc-parser` 小且能给出精确错误位置。

**校验**：所有配置加载后过 zod schema；未知字段给出警告而非静默忽略。

### ADR-009：会话使用 JSONL 追加写

**候选**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| JSONL 追加 | 崩溃安全、可流式读、diff 友好 | 查询能力弱（需全量扫描） |
| SQLite | 查询强、事务 | 原生模块、跨机器兼容、文件体积 |
| 单 JSON 全量重写 | 简单 | 崩溃丢全文件、U 盘写入放大 |

**决策**：JSONL + `index.json` 索引。

**理由**：U 盘场景最怕"热拔/断电写坏"，追加写天然安全；会话检索需求弱，全量扫描可接受。

**实现细节**：

- 每条消息一次 `write` + `fsync`（可配置为批量 flush 以换性能）；
- 启动时校验最后一行，损坏则截断到最后一条完整记录；
- 会话文件按 `projectKey` 分目录，避免单目录文件过多。

### ADR-010：密钥存储与可选加密

**决策**：

- 默认写入 `config\secrets.json`，明文，启动时打印一次风险提示；
- 可选口令加密：`scrypt` 派生 → `AES-256-GCM`，密文存 `secrets.enc.json`；
- 环境变量优先级最高（`AGENT_<PROVIDER>_API_KEY`）。

**理由**：便携场景下没有系统钥匙串可用（exFAT 无 ACL），只能靠"加密口令 + 用户自律"。该限制必须在文档中明示。

**否决**：Windows DPAPI 加密——绑定当前用户与机器，换机后无法解密，违背便携目标。

## 7. 扩展

### ADR-011：使用官方 MCP SDK

**决策**：`@modelcontextprotocol/sdk`（client 部分），支持 stdio 与 Streamable HTTP。

**理由**：MCP 协议仍在演进，自研容易在握手、能力协商、通知上踩坑；官方 SDK 与生态一致。

**后果**：打包时需确认 SDK 的 ESM 结构可被 esbuild 正确处理；MCP Server 若用 `npx` 启动会写 C 盘缓存，需在 `/doctor` 中检测并提示。

### ADR-012：Skills 使用 YAML frontmatter + Markdown 正文

**决策**：与 Claude Code 的 Skill 形态对齐（`SKILL.md`），使用 `yaml` 解析 frontmatter。

**理由**：格式简单、用户可直接编写；渐进披露（只注入元数据）能显著节省上下文。

## 8. 构建与打包

### ADR-013：esbuild 单文件 bundle

**候选**：

| 方案 | 文件数 | 构建速度 | 运行性能 | 备注 |
|---|---|---|---|---|
| tsc + node_modules | 数千 | 慢 | 中 | U 盘小文件性能灾难 |
| esbuild bundle | 1 个 JS + 少量资源 | 极快 | 好 | 需处理动态 require / 原生模块 |
| webpack | 1~数个 | 中 | 好 | 配置复杂 |
| bun build | 1 个 | 快 | 好 | 构建链引入 Bun，增加工具依赖 |

**决策**：esbuild `--bundle --platform=node --format=esm --target=node24`，产物 `app\dist\cli.js`。

**注意**：

- Ink/React 的 `process.env.NODE_ENV` 在构建时用 `define` 固定为 `production`；
- 仅 `rg.exe`、Node 运行时为外部文件（不可 bundle 的原生二进制）；
- 动态 `import()` 若必须保留，需在 esbuild 中标记 external 并在 `app\` 中保留对应文件；
- 构建后进行冒烟：`node dist/cli.js --version`。

### ADR-014：目录布局与更新方式

**决策**：

```text
runtime\win-x64\   只读，随版本替换（预留 linux-x64 / darwin-arm64）
app\               只读，随版本替换
tools\             只读，随版本替换（rg.exe 按平台，v2 增加 linux/darwin 版本）
config\            用户数据，升级不覆盖
data\              用户数据，升级不覆盖
memory\            用户数据，升级不覆盖
skills\            用户数据，升级不覆盖
agents\            用户数据，升级不覆盖
commands\          用户数据，升级不覆盖
```

升级方式：解压新版本到临时目录 → 替换 `runtime/app/tools` → 保留其余目录 → 运行 `/doctor` 校验。v1 不实现自动更新，只提供 `scripts\upgrade.ps1`（手动执行）。

### ADR-015：平台抽象层（跨平台预留）

**背景**：v1 只交付 Windows，但用户明确要求未来扩展到 Linux/macOS，并完善生态适应性。如果现在把 PowerShell、盘符、`\r\n`、`process.platform` 分支散落到业务代码，v2 的重构成本会非常高。

**决策**：定义单一 `PlatformAdapter` 接口（见《02-架构设计》12.5），平台差异只允许出现在 `src\util\platform.ts` 与其实现中。

**落地要求**：

- 路径一律 `path.join` / `path.resolve`，禁止字符串拼接分隔符；
- Shell 调用一律经过 `platform.defaultShell()`；
- 文本读写保留原始换行；
- 文件大小写比较走 `caseSensitiveFs()`；
- 终端能力用探测而非平台判断；
- 构建脚本接受 `--target win-x64|linux-x64|darwin-arm64`；
- 平台相关单测参数化。

**后果**：v1 增加少量抽象成本（约 1~2 人日），换取 v2 的低成本移植；v1 功能与体验不受影响。

## 10. 性能预算

| 指标 | 预算 | 测量方式 |
|---|---|---|
| 冷启动（到可输入） | < 2s（USB 3.0） | 日志时间戳 |
| 空闲内存 | < 250MB | 任务管理器 |
| bundle 体积 | < 8MB | 构建输出 |
| 会话追加写延迟 | < 10ms/条 | 基准脚本 |
| Grep 10k 文件仓库 | < 1.5s | 基准仓库 |

若超出预算：优先减少启动期同步 IO（MCP 懒连接、技能懒扫描），而不是牺牲功能。

## 11. 依赖策略

- 生产依赖控制在 **15 个以内**，每个都需说明用途；
- 禁止引入需要 postinstall 编译的包（U 盘与离线环境不可控）；
- 禁止引入遥测/分析类依赖；
- 所有依赖锁定版本，提交 `package-lock.json`；
- 每次升级依赖后必须跑完整测试 + 便携冒烟。

### 预计生产依赖清单

| 包 | 用途 |
|---|---|
| `ink`, `react` | TUI |
| `zod` | schema 校验 |
| `tinyglobby` | 文件匹配 |
| `marked` | Markdown 解析 |
| `cli-highlight` | 代码高亮 |
| `@modelcontextprotocol/sdk` | MCP 客户端 |
| `jsonc-parser` | 配置解析 |
| `yaml` | frontmatter 解析 |
| `diff` | 编辑预览 |
| `string-width` | 终端宽度计算（Ink 依赖，显式声明） |

（`typescript`、`esbuild`、`vitest`、`biome`、`tsx` 为开发依赖，不进入产物。）
